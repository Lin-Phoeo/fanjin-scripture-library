## 1. 直接结论：先试哪一套

**建议把 T3 Code 作为统一工作台的首个试点候选，组合为 T3 + Codex CLI + Claude Code + 一个可选的 OpenCode 工作者 + 每任务 worktree + 项目现有质量门禁。试点通过后，再将它设为日常默认。**

你的痛点是多个渠道、多个编码终端各自工作，却要你负责搬运需求和结果。T3 的价值是把入口、渠道实例、会话和委派收在一个地方；负责人可以向明确的实例派工。这个推荐有固定版本文档和源码依据，但尚未经过你这台 Windows 上的真实渠道联调，不能说已经比其他工具更稳定、更快。〔S01–S04〕

**不愿更换现在的 Codex/Claude 主入口，就选 HMB。** 完整组合是“现有主助手 + Hey-my-buddy + Codex/Claude/DSH 工作者 + 受管 worktree + 现有门禁”。但 HMB 0.69.7 不能直接被当作同一 Codex/Claude 下任意多端点的实例切换器；多渠道要求应优先核对其实际目录和 DSH 路由。〔S05〕

**如果多数项目已经通过 issue、PR 和 CI 推进，就优先选 AO。** 完整组合是“Orchestrator.inc + 各项目负责人 + 原生 CLI 工作者 + worktree + GitHub PR/Actions”。这里的 AO 明确指 `OrchestratorInc/agent-orchestrator`，不是搜索结果中所有同名项目。〔S06〕

| 你的主要偏好 | 我建议的入口 | 具体理由 |
| --- | --- | --- |
| 一个界面管会话、多个渠道和项目 | **T3 首试** | 有明确 provider 实例和内部委派接口 |
| 保留当前 Codex/Claude，不再手工传话 | **HMB** | 主助手负责理解和验收，桥接层负责派发和回收 |
| 多项目按 PR、CI 和审阅意见推进 | **AO** | 工程闭环和任务状态比会话组织更重要 |
| 不执着于多个品牌终端，只需要多种 API 模型 | **OpenCode 原生或 DSH 原生** | 减少跨运行时翻译与配置数量 |
| 想把实现、审阅、返工画成可视流程 | **Worktree Kanban** | Pipeline、分支和 Join 更直观 |
| 必须看到真实终端，后续还要跨机器 | **Herdr/hc** | 终端托管、发送、读取、等待与 SSH 适合这类需求 |

这里选一个主编排入口即可。T3、HMB、AO 不应同时拥有同一批任务的启动、取消和工作树回收权。

## 2. 你真正需要的协作结构

一个主会话只用一个模型，不意味着整个项目只能用一个模型。合理结构是一个负责人把不同任务交给不同运行时；每个运行时再绑定自己的渠道和模型。

```text
你：在一个入口给目标与验收条件
  └─ 负责人：拆任务、冻结接口、派发、收结果、集成
       ├─ 工作者 A：渠道 A / 模型 A / 工作树 A
       ├─ 工作者 B：渠道 B / 模型 B / 工作树 B
       └─ 独立审阅：另一会话，按固定差异和验收要求检查
            └─ 负责人：完整门禁 → 可交付结果 → 范围内发布

Gemini Deep Research + 已有 DSH 调研链路 → 来源材料 → 负责人核验
```

| 层次 | 实际负责什么 | 常见误判 |
| --- | --- | --- |
| 模型渠道 | 地址、协议、模型 ID、凭据、额度、并发 | 标着 OpenAI 兼容，就认为所有编码 CLI 都可用 |
| 编码运行时 | 读写文件、工具调用、命令、上下文和恢复 | 把 Claude Code、Codex、OpenCode、DSH 当作模型名称 |
| 编排入口 | 派工、等待、回传、取消和状态 | 多开几个窗口就算自动协作 |
| 文件与任务隔离 | 固定输入、独立修改副本、成果身份 | 不同 session 或 cwd 就天然不会互相覆盖 |
| 集成与验收 | 审差异、合并、完整检查、发布证据 | 工作者说“完成”就认定应用交付成功 |

worktree 只提供独立工作副本，仍共享部分 Git 元数据，也不限制同一账户的文件访问。实例配置、文件隔离、运行权限是三个不同问题。

## 3. 六套能解释清楚的完整组合

### 组合 A：T3 统一工作台，作为首个试点

**组成：T3 Code + Codex CLI + Claude Code + 可选 OpenCode + T3 受管 worktree + 项目 CI。**

你在 T3 的项目线程输入目标，负责人也运行在 T3 内。负责人通过内部 `delegate_task` 指定目标实例，并显式为独立写任务选择 `isolation: worktree`；跟进任务状态，读取成果，再统一整合。不要假设当前外部 Codex 连上 T3 MCP 就会自动获得内部委派身份。

| 起始角色 | 使用什么 | 具体任务与配置归属 |
| --- | --- | --- |
| 负责人 | 当前稳定的 Codex/GPT 渠道 | 规划、公共契约、汇总、集成；在 T3 内运行 |
| 实现 A | Codex 实例 A | 数据、业务、性能；需要多端点时使用独立 home |
| 实现 B | Claude 实例 B | UI、交互或另一块实现；实例环境/配置目录固定 |
| 可选常规工作者 | OpenCode + 其原生渠道 C | 文档、测试、独立局部修改；不在首轮额外增加并发 |
| 独立审阅 | 与主要实现不同的已验证模型、独立会话 | 读取集成差异和要求，报告可证实问题 |

这里按工作范围分工，不是宣称某个品牌天然只适合前端或后端。模型 ID 使用你实际渠道中已验证的编码型号，不编造统一的“最强组合”。

**渠道接法有具体依据：** `target.providerInstanceId` 可锁定实例，另配 `model/options`；显式指定的实例不可用时会失败，不应静默换成另一实例。Claude 支持实例环境变量区分 endpoint/key；独立账号需要相应配置目录。Codex 的独立 home 隔离配置与会话，而 shadow home 主要拆分登录、仍共享配置与会话，不能用来保证多端点隔离。〔S01–S04〕

**重要限制：**委派默认是 `shared`；worktree 从父提交创建，不带父未提交修改。跨 linked environment 的内部 delegate 不接受 worktree，需要采用 `t3_thread_launch` 的 worktree 策略。当前契约没有 Gemini 所说的 `outputSchema` 和 `t3_submit_output`；输出强验收仍由负责人落实。

**新增负担：**一个工作台、实例配置和验证；保留原生 CLI。OpenCode 可以后加，不必首次就接入三种运行时。适合你愿意统一日常入口、以后管理多个公益项目的目标。

### 组合 B：当前主助手 + HMB，降低入口迁移

**组成：当前 Codex/Claude Host + HMB + 一个 Claude/Codex 工作者 + 一个 DSH 工作者 + HMB 受管 worktree + 现有门禁。**

你继续在当前主助手里下需求。主助手读取 HMB 能力和可用目录，派发任务，接收固定产物，退回补做或验收。HMB 提供任务记录、输入固定、产物封存、续做/取消和 Host 验收身份；主助手负责判断是否符合需求、跑测试和集成。看板用于观察，不必迁移全部日常会话。〔S05〕

**必须修正的渠道边界：**0.69.7 的 Codex 发现过程默认只根据当前 `config/read.model_provider` 建目录桶；执行确实会传请求的 `modelProvider`，但这不证明能同时注册多个 home/endpoint 实例。Claude 发现使用当前初始化得到的 API provider，执行主要传 model/effort，没有已证实的逐任务 endpoint/home 切换。DSH 则可枚举 ACP 声明的多个 `[provider, model]` 并按会话选择。

所以明确可试的是“Codex 当前渠道 A + Claude 当前渠道 B”，或“某原生 CLI 当前渠道 + DSH 已登记的另一渠道”。如果你要同一种 Codex/Claude 同时连接多个站点，先核清目录与实例能力；不能因为请求里有 `provider` 字段就宣布解决。

**新增负担：**0.69.7 需要 Python `>=3.12,<3.13`、HMB 运行时与 skill，以及工作者识别。已核工作者范围为 Codex、Claude、DSH、ZCode，不能直接把 OpenCode/Gemini CLI 填入。它过滤某些 shell 密钥与 endpoint 覆盖，不能假设父终端临时环境会原样进入工作者。

适合你的条件是“主聊天入口不能换、现有原生渠道已能用”。Windows 后台、真实并发和停止恢复仍需试点；七项离线测试只证明其对应函数。

### 组合 C：AO + PR/CI，面向多项目持续开发

**组成：Orchestrator.inc + 每项目负责人 + 原生 CLI 工作者 + 每任务分支/worktree + GitHub PR/Actions。**

你在工程看板看任务、差异、PR 和 CI。项目负责人派发有边界的实现，工作者返回自己的分支成果；CI 失败、审阅反馈和冲突由相应代理处理，负责人整合。模型渠道由底层 CLI 承担，AO 适配器存在不代表账号或第三方服务已就绪。〔S06〕

它更适合“多个站点长期维护、issue/PR 是主要任务入口”的阶段。T3 偏日常会话和实例组织；AO 偏工程任务闭环，二者按你的主流程二选一，不按项目个数机械迁移。

**具体边界：**v0.15.3 中各 harness 的 TUI、Chat、Reviewer 能力不同；Gemini 的 TUI 支持不能外推为同等 Chat/Reviewer。Git 项目使用 worktree；projectless 是普通受管目录。CI reaction 的重试/升级应按所选版本和事件设置，不能推定全局有统一重试上限，更不能把自动回修等同自动合并发布。

**新增负担：**工作台、项目与 CLI 配置、GitHub 连接、反馈策略。Windows #8495 是 0.15.1 的问题报告，维护者未在 Win11 复现；应加入试点检查，而不是笼统宣布 Windows 不可用。〔S06、S19〕

### 组合 D：原生多模型，减少跨终端桥接

**组成：OpenCode 多 provider/agent + 已验证角色路由 + 负责人预建 worktree + 项目门禁。DSH 原生 spawn 可作为替代宿主。**

如果你的真实要求是多个模型配合，而不是多个品牌的终端本身，这条路线更轻。负责人、实现者和审阅者都由同一运行时执行，不同角色绑定不同 provider/model。你只开一个主入口；独立写入仍需明确的 worktree 和任务所有权。

OpenCode 的自定义 provider 和原生 agent 路由有官方依据，但大版本配置已变化。Context7 本次返回同时含 v1 路径和当前路径：v1 的 Chat Completions provider 使用相应 compatible SDK，Responses 则使用对应 SDK；新版权限字段也不同。**因此本报告不给一份混合两代字段的“复制即用 JSON”。** 先锁定实际版本，再生成通过 schema/原生启动验证的配置。〔S08〕

若使用现有 DSH，其 spawn 可在已登记、允许的路由中选择模型；默认 fork 继承父模型，新会话选路和旧会话续接不能混为一谈。本机曾发现桌面随附、插件和 PATH 入口版本不同，实际 Host 加载版本仍须在试点预检核实。10 项 helper 检查并不证明当前 Host 已加载该包。〔S09〕

**新增负担：**一个运行时的角色、渠道和权限配置；无需为了跨品牌先增加桥接层。适合 API 渠道多、预算敏感、可以接受统一工具体验的场景。

### 组合 E：Worktree Kanban，可视化固定流程

**组成：Worktree Kanban + Codex 实现 + Claude 审阅 + 可选 OpenCode + Pipeline + 外置完整门禁。**

你把目标放到卡片；流程可设为“并行实现 → Join → 完整检查 → 审阅 → 一轮定向返工 → 负责人验收”。v0.2.18 文档列出 10 类 CLI，包括 Claude、Codex、Gemini、OpenCode 等，能力各异；不是 Gemini 报告写的 5 类。〔S07〕

串行步骤默认共用任务工作树，会传递报告且每步提交；因此“审阅步骤”不能自动称为隔离的严格只读审阅。并行分支有各自 worktree，Join 仍可能冲突；进入 Review 列或到达循环上限也不等于门禁通过。实际模型不匹配时部分后端可能回到默认并记日志，验收必须核生效选择。

**新增负担：**工作台、Pipeline 定义和 CLI 配置。许可为 FSL-1.1-ALv2，内部开发使用和再分发/提供竞争服务应分开评估。适合固定重复流程，作为 T3/AO 的替代入口。

### 组合 F：Herdr/hc，终端与跨机器优先

**组成：Herdr App/hc + 角色 CLI 启动模板 + 负责人预建 worktree + Git + 统一门禁。**

负责人通过 `hc run/send/read/wait` 操作真实代理终端；你可以 attach 检查或接管。以后用明确的 SSH 连接扩展到另一台机器。模型、endpoint、认证由对应 CLI 启动模板和原生配置负责，hc 不是统一模型网关。〔S10〕

主 Herdr 0.9.5、独立 hc、独立 App 不能拼成同一代接口。主项目部分状态来自屏幕检测；独立 hc 强调程序状态上报。不报告状态的工具不能因输出安静就认定任务完成。Windows 模板/引用 shell 命令还需要可用的 `sh`，例如 Git for Windows；中文 IME、attach 和恢复能力按具体产品核验。

**新增负担：**终端总控与模板，以及原有 CLI；工作树和验收由负责人安排。适合真实终端和多机是硬需求时。对于你当前“减少搬运、同机多项目交付”，优先级低于 A/B/C。

## 5. 多渠道究竟怎么接：协议和配置先分开

| 入口 | 渠道应由哪里绑定 | 上线前必须核实 |
| --- | --- | --- |
| Codex CLI | 原生 provider 配置；需要隔离时用明确的独立 home | Responses 及运行时预期行为、工具调用、模型 ID、认证、恢复作用域 |
| Claude Code | 原生设置、实例环境、独立配置目录 | Anthropic Messages 兼容性、工具/流式、实际 Claude 服务与其支持边界 |
| OpenCode | 所选大版本的 provider SDK 和 agent 路由 | Chat/Responses/Gemini 等对应适配，schema 和实际工具往返 |
| DSH | 实际 Host 加载版本中的 adapter、路由和会话授权 | 注册路由、动态选路开关、allowlist、会话绑定 |
| Gemini Deep Research 网页 | 研究输入渠道 | 不把网页订阅直接当 API 编码工作者 |

仅有 `/v1` 地址和模型名称不够。一个服务能正常聊天，也可能缺失编码工具需要的增量 tool-call、长工具结果、取消、流式结束事件或续接能力。先做极小原生读文件往返，再谈并发。

**不靠反复切 CC Switch 全局当前渠道实现并发。** 各任务启动时应固定实例/配置源，并记录 provider/model 的实际读回。两个不同地址也可能共用物理上游；第三方回显的模型名只能算服务端声明，不能独立证明底层模型身份。

### T3 与 OpenCode 的版本注意事项

已核 T3 v0.1.11 文档支持 OpenCode 1.14.19+（1.x 为 Limited support），2.0.18+ 可自动识别。OpenCode 2 使用 `@opencode/cli`，首跑会迁移共享数据库；官方明确不要在同一机器同时运行 v1 与 v2。T3 不会自动跨大版本升级 OpenCode。首次试点只固定一个兼容代际，不能为了并行工作者把两代一齐开着。〔S03〕

## 6. 给你的起始团队与运行方式

**初始只设一个负责人、两个可并行工作者、一个随后进行的独立审阅步骤。** 研究放在开发循环外按需执行。并发值是试点起点，不是所有服务的统一行业限制。

| 配置档 | 负责人 | 同时实现 | 审阅 | 适用情况 |
| --- | --- | --- | --- | --- |
| 先证明可行 | 当前稳定渠道 | 1 个另一渠道 | 独立会话随后做 | 新工具/新渠道尚未联通 |
| 推荐起点 | 当前稳定且熟悉项目的模型 | 2 个互不重叠任务 | 不同于主要实现者的会话 | 大多数日常开发 |
| 控制费用 | 保留较强负责人 | 1 个适配常规任务的低成本渠道 | 关键差异用稳定渠道审 | 额度波动或返工高 |
| 多项目持续维护 | 每项目明确负责人 | 受总额度限制的任务队列 | 每 PR 独立审阅 | AO 等工程工作台成熟后 |

“实现 A 用 GPT、实现 B 用 Claude、常规任务用 DeepSeek/Qwen/Gemini”只是可替换的起始分工。实际选择取决于渠道质量、工具兼容、限流和测量结果；不把模型品牌等同能力保证。

每个子任务只需要：目标、相关路径、固定 base、禁止破坏的不变量、文件所有权、验收命令和返回成果。不要把全部长聊天复制给每个工作者，重复付出上下文和协调成本。

## 7. 用梵烬演示一轮实际开发

可以用这个目标作为后续真实试点：**“优化大部经典加载，保留书目/段落 slug、书签、心得快照、阅读位置、简繁行为与现有视觉。”** 它是建议的试点题目，本次没有实施该功能。

1. **负责人先做接口约定。** 确认按章/分块加载的结构、回退行为和已有索引兼容性；公共类型与依赖锁文件由单人负责。
2. **数据工作者在 A 工作树实现。** 负责构建输出与加载层，返回固定 commit/patch、变更范围和检查结果。
3. **界面工作者在 B 工作树实现。** 依已冻结契约处理加载状态、错误重试与阅读定位，不重做整站设计。
4. **负责人集成到专用副本。** 检查提交后差异、暂存、未暂存与新文件，处理冲突；不用持续变化的 main 代替固定 base。
5. **独立审阅检查兼容性。** 核旧记录、段落身份、网络中断、长文定位、简繁和本机私有数据边界。
6. **运行 `npm run check:release`。** 构建与隔离浏览器验收对应同一集成代码和同一产物，不验证旧 dist；需要发布时再核对应提交的 Actions 和线上内容。
7. **按归属收尾。** 自建测试 context、标签、服务和可回收工作树逐项处理；保留用户浏览器与未知执行成果。

这轮最理想的变化是：你只给一次目标、查看一次整合结果，负责人承担派发、读取和验收。是否更快，必须把准备、协调、返工和完整检查时间都算上。

## 8. Windows、恢复与资源：需要验的具体场景

### 8.1 配置、代理和工作区

继续使用已经固定的代理 **7890**。本轮不改端口、不重启 NAT、不批量修改 ACL。若将来网络失败，先区分代理监听、系统排除端口、运行时协议和上游限流，不靠更换渠道反复重跑掩盖问题。

配置目录可能包含登录资料，新建目录不自动继承认证。worktree 也不自动带入父工作区未提交文件。测试使用独立数据、端口和浏览器环境；端口冲突时修改本次测试端口或明确失败，不停用户服务。

### 8.2 停止必须能证明归属

“取消请求已发送”和“执行确实停止”应分开记录。Windows Job 有助于控制执行树，但必须验证加入成功和退出状态。裸 PID 加 `taskkill /T` 不足以长期证明归属，存在 PID 复用、父进程先退和后台子进程脱离问题。

推荐至少区分：queued、running、cancel_requested、stopping、delivered、accepted、failed、shutdown_unknown。处于 shutdown_unknown 时保留成果与占用，不自动重派、不强删工作树。

清理只认本次创建清单。不能递归删除共享 `wt`/`homes` 父目录；不能要求全机只剩一个 worktree；移除失败就保留并报告。home 里可能有登录状态，不能作为临时垃圾统一清空。

### 8.3 恢复与限流

同一个逻辑任务需要 run/task/attempt 身份、原生 session、固定输入摘要和产物身份。`state.json` 存在不等于幂等；调度器重启后先核已有执行，不能直接重派。

429 要区分原生 CLI 内部重试与编排重试，不能双重无界退避。模拟 HTTP 429→200 只证明退避函数，不证明实际 CLI 会暴露 Retry-After 或已经正确取消。建议首次把自动返工限制为一轮，网络重试和代码返工分别计数；这是试点设置，实际产品是否原生支持须核所选版本。

## 10. 有限试点：怎样才算真的能用

详细步骤在 [试点执行单](02-试点执行单.md)。以下是阶段门槛，任何一阶段失败就停在该阶段定位，不用叠加另一套编排器救场。

| 阶段 | 执行什么 | 通过条件 |
| --- | --- | --- |
| 0：准备 | 版本、固定 base、已有资源、配置作用域、协议和预算字段 | 不存在身份或配置串线疑点；不发模型请求 |
| 1：两渠道原生往返 | 各做一次极小读文件任务 | 实际终态、产物和渠道身份有证据；资源停止 |

## 11. 成本和提速：用什么指标决定留下它

没有实际渠道账单和相同任务实验，不能承诺提速倍数、节省比例或固定安装工时。公益模型站价格、额度、排队和供应会变化，公开宣传也不能代替你实际账号的可用性。

成本应包含负责人、工作者、审阅、失败重试、重复上下文和集成返工。如果各渠道有可用计价：按其实际输入/缓存输入/输出计费项逐项算；包月或公益额度另记消耗、限额与阻塞时间，不能一律当零。

| 指标 | 应记录什么 | 为什么 |
| --- | --- | --- |
| 完整交付时间 | 从接受任务到同标准验收，含准备/协调/返工 | 避免只比代码生成速度 |
| 人工介入 | 用户传话、手抄结果、修配置、处理冲突的次数/时间 | 回答你的主要痛点是否消失 |
| 用量和费用 | 各角色原生用量、实际账单，缺失记 unknown | 防止“没有字段＝免费” |
| 质量 | 独立审阅、完整门禁、验收后缺陷 | 并发不能用降低质量换速度 |
| 恢复和清理 | 是否重复派发、残留自有资源、未知终态 | 判断能否长期使用 |

优先保留一个负责人和真正可并行的两个任务。公共接口、集成、最终验收通常有先后关系；模型数增加不会使这些串行步骤消失。先用一轮验证可行，再用多轮相近任务判断长期收益。
