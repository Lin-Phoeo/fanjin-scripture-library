# 六套完整协作组合：给当前环境的明确建议

日期：2026-11-21。依据已完成的开放式调研和Gemini报告复核。这是架构与试用建议，不是六套软件已在本机跑通的声明；没有安装或变更渠道。

## 我的明确选择

**长期主方案：T3 Code + Codex CLI + Claude Code + OpenCode + Git worktree + 项目现有CI。**

原因：你的核心需求不仅是多派几个子代理，还包括多个模型站、多个项目、一个看得见的工作入口，以及不再自己在终端之间搬运任务。T3已核实的provider实例配置、统一会话与worktree组织，比单纯增加分屏更贴近这个日常使用目标。这里选择T3为主入口，因此主代理也运行在T3内，内部委派才具备所需调用者身份。

**保留当前主入口的备选：现有Codex/Claude + HMB + Claude/Codex/DSH Worker + Git worktree + 现有CI。**

此前建议HMB先小试点，指的是少迁移、先验证协作收益；并非断言HMB是你长期桌面的唯一最佳答案。若你不想换主聊天入口，选这套即可；若愿意统一到工作台，直接评估T3，不必先安装HMB。

两者不叠加管理同一个任务。尚缺的是真实渠道、协议与本机端到端验证，不是再搜索更多名字。

## 组合一：统一工作台，适合你长期日常使用

**组成：T3 Code + Codex CLI + Claude Code + OpenCode + worktree + GitHub Actions / 本地check:release。**

| 部件 | 具体作用 |
| --- | --- |
| T3 Code | 你发任务、看进展、读差异和收结果的唯一工作台；负责人在T3内部运行 |
| Codex负责人 | 起始选用你当前能稳定使用的GPT模型，拆任务、定义接口、检查结果、统一集成 |
| Codex执行者 | 接Responses兼容渠道A，承担数据逻辑/功能实现；与负责人使用独立任务会话 |
| Claude Code执行者/审阅者 | 接Anthropic Messages兼容的Claude渠道B，承担UI实现或审阅；角色可以轮换 |
| OpenCode执行者 | 接其原生支持的渠道C，例如Chat Completions兼容的DeepSeek/Qwen/Gemini模型服务，做范围清楚的测试/文档/局部实现 |
| worktree和CI | 每个并行写入任务有独立副本；负责人整合后运行真实门禁 |

**你怎么用：**在T3项目里告诉负责人“完成梵烬大经按章加载，保留书签与简繁行为”。负责人先定数据契约，再把数据模块和UI模块分别派给不同工作者，最后让独立会话审阅、运行check:release，向你展示一个整合结果。

**模型渠道怎么接：**provider实例各有明确配置来源，不通过反复切换CC Switch全局当前渠道。只改变接口/密钥的Claude实例可使用实例环境；独立账号使用其支持的配置目录。Codex和OpenCode也按所选版本核对实例与原生配置。渠道必须有实际工具调用与流式响应能力，仅会聊天不够。

**新增成本：**安装T3；若OpenCode当前入口不可用，再准备其兼容版本。保留现有CLI。无需为了这套组合先装WSL/tmux；具体后端Windows行为仍要验证。

**关键限制：**T3 v0.1.11的delegate默认共享checkout，写任务必须显式worktree；没有报告误写的outputSchema强验收。门禁由负责人执行和读取，不是T3界面显示完成就自动全绿。外部Codex连接T3时用thread API，不与内部delegate混为一套。

**推荐程度：长期主选。** 这是日常入口的推荐，不是已证实比其他工具更快的性能结论。[1][2]

## 组合二：继续用当前Codex/Claude，自动找其他模型帮忙

**组成：现有Codex或Claude Host + Hey-my-buddy + Codex/Claude/DSH Workers + managed worktree + 现有CI。**

起始搭配：你仍在Codex里说需求；HMB把实现任务发给一个Claude Worker，把测试或资料任务发给DSH Worker，负责人再调用独立Codex/Claude会话审阅。DSH Worker可用其原生配置提供不同模型渠道，HMB不要求大家使用DeepSeek模型。

HMB负责任务记录、输入固定、输出封存、继续/退回/取消和验收身份；Host负责真正理解需求、检查产物与整合代码。其Web看板用于查看任务，不强迫你迁移所有日常聊天。

**你怎么用：**在现有主助手下达“两个任务并行，完成后互相审阅，只把通过验收的成果交给我”。主助手读取HMB能力、派发和跟进，用户不再来回复制回复。

**新增成本：**HMB运行时与skill、一次Worker识别及配置确认。已核0.69.7需要Python3.12；不需要T3或Herdr同时管理任务。

**关键限制：**已核HMB Worker只支持Codex、Claude、DSH、ZCode，不直接支持OpenCode/Gemini CLI。模型密钥与endpoint只放在当前shell里的接法不能假设会传入Worker；HMB过滤这些变量，须通过对应harness原生配置确认。Windows后台服务存活、跨渠道并发和取消仍要做实际试点。

**推荐程度：不换主入口时的首选。** 同时也是低迁移成本的协作验证路线。[3]

## 组合三：多个项目持续推进，PR和CI形成闭环

**组成：Orchestrator.inc + 项目负责人代理 + 各CLI Workers + 每任务worktree + GitHub PR/Actions。**

为梵烬和其他项目分别建项目负责人，任务由各负责人派给Codex、Claude、OpenCode等实际可用适配器。工作者提交到自己的任务分支；CI失败、审阅意见和合并冲突返回相应负责人/工作者处理。

**你怎么用：**从统一看板查看哪些项目正在实现、等审阅、测试失败或可集成。你优先处理需要产品判断的事项，模型负责有边界的修复循环。

**与组合一的差别：**T3更适合作为会话和渠道实例的日常主入口；AO更突出任务、PR、CI与分支负责人的闭环。你若已经把多数工作通过issue/PR管理，可直接把AO提升为主选；无需按项目数量机械迁移。

**新增成本：**一个桌面/后台工作台，项目与CLI发现、GitHub连接；不要求恢复梵烬应用服务器。

**关键限制：**自定义渠道仍由底层CLI承担，登记适配器不等于账户就绪；v0.15.3中不同harness的TUI/Chat/Reviewer能力不一致。只在Git项目任务上谈worktree，projectless是普通受管目录。必须设置有界返工，CI反馈不等于无限自治发布。

**推荐程度：PR/CI成为日常工作主轴时的升级路线。**[4]

## 组合四：主要使用模型API，减少不同终端的管理成本

**组成：OpenCode多provider/多agent + 精确角色路由 + 负责人准备的worktree + 现有CI。**

所有角色运行于同一编码环境：规划角色接渠道A，执行角色接渠道B，审阅角色接渠道C。每个角色显式设置provider/model，依任务选择工具与权限；只读可并行，写入副本由负责人明确准备。

如果你更熟悉DSH，也可以使用 **DSH原生spawn + 已授权的不同模型路由 + 相同worktree/验收纪律** 作为这条路线的替代宿主，而不是再套HMB。

**你怎么用：**只打开一个原生助手入口，多模型能力在其内部配置完成。适合“我关心哪个模型干什么，不在乎它来自哪个品牌终端”的用法。

**新增成本：**配置一个运行时的多渠道、角色与写入边界。现有宿主已满足协议时成本更低；但不能为减少软件数量丢掉当前必需的CLI能力。

**关键限制：**不同角色或cwd不自动等于独立文件副本；官方订阅与API认证不能互换。DSH默认fork继承父模型，spawn选路设置还与新Session绑定。遇到具体协议不兼容才考虑网关，不默认再加一层。

**推荐程度：大量第三方API、预算敏感且可接受一个主运行时时的备选。**[5]

## 组合五：希望看到“实现→审阅→返工”的固定流程

**组成：Worktree Kanban + Codex实现 + Claude审阅 + 可选OpenCode Worker + Pipeline + 外置质量门禁。**

建立可视流程：数据实现与UI实现并行 → Join整合 → 项目门禁 → 审阅 → 最多一次定向返工 → 等待负责人验收。已核v0.2.18支持10类CLI入口，而非Gemini报告说的5类。

**你怎么用：**把任务放进卡片，按预先定义的Pipeline推进；当失败或条件不匹配时停在相应步骤。适合经常重复同一种开发流程，希望少写编排提示词的场景。

**新增成本：**工作台和Pipeline配置；CLI使用自己的登录与模型设置。

**关键限制：**串行步骤默认共享任务工作树并传递上一阶段报告，不能自动称为独立只读审阅；每步会提交。并行分支虽有独立worktree，合并仍可能冲突。进入Review列、达到循环上限都不等于检查通过；OpenCode等后端模型不匹配可能回到默认并记日志，必须检查实际选择。

**推荐程度：明确偏好可视流程图时选它，与T3/AO互为替代入口。**[6]

## 组合六：需要看着多个真实终端，并且将来跨机器

**组成：Herdr App/hc + 每角色CLI启动模板 + 负责人预建worktree + 统一Git与门禁。**

一个负责人用hc启动、发送、读取、等待其他终端；每个角色模板调用自己的CLI与配置。你随时attach到某个终端检查或接管。以后若需远端机器，可通过明确的SSH连接扩展。

**你怎么用：**把它当多个真实代理终端的总控制台；能够看见输出、补充任务和处理被阻塞的执行，不靠原生桌面App之间互点聊天框。

**新增成本：**hc和可选App，以及现有CLI；Windows模板/引号命令需要可用sh。模板中的角色文案不建立worktree，也不构成权限沙箱。

**关键限制：**仍由负责人准备文件隔离和验收。hc的状态来自程序上报；没有状态的程序不能因输出安静就判断完成。主Herdr TUI与独立hc代际不同，命令和配置必须匹配版本。

**推荐程度：终端/多机优先时合适；你的当前首要需求是单机多项目交付，我把它排在前面几套之后。**[7]

## 所有组合都能复用的研究层

**Gemini Deep Research + 你已配置的DSH研究链路 → 有来源的调研材料 → 负责人核验 → 开发任务。**

Gemini Deep Research负责开放搜索、对照和资料整理，DSH链路补原文抓取、代码/文档核验，负责人吸收后形成具体任务。这正是你刚才让Gemini协助的方式。

网页里的Gemini Deep Research不是可直接当并发Worker使用的API。若要代码工作者使用Gemini模型，另用受支持的Gemini API/CLI或原生runtime接入，并核协议与额度。研究报告里的命令和结论也不能自动变成执行授权。

## 为你建议的起始团队

这是可调整的起始角色分工，不是模型品牌能力排名；具体型号按你实际渠道可用列表选。

| 角色 | 起始安排 | 负责什么 |
| --- | --- | --- |
| 负责人 | 当前已熟悉项目的Codex/GPT；若选T3则在T3内创建该负责人 | 分解任务、冻结接口、汇总与集成 |
| 实现A | Codex/GPT编码模型 | 数据读取、业务逻辑、性能修改 |
| 实现B | Claude Code/Claude模型，或实际更稳定的另一路模型 | 阅读UI、交互、测试；不默认与A争改同文件 |
| 常规任务 | OpenCode或DSH承接DeepSeek/Qwen等可用模型 | 测试整理、文档、范围清晰的独立修改 |
| 独立审阅 | 与主要实现不同的模型、独立会话 | 只读差异与验收要求，不照抄实现者自述 |
| 研究 | Gemini Deep Research与既有DSH研究工具 | 扩展信息、原文核验，不直接改生产代码 |

初始并发为两个工作者，审阅随后运行。相同逻辑任务尽量维持同一渠道以保留上下文与缓存；不能用无界fallback在多个模型站间来回重跑。

## 用梵烬演示一次真正协作

你只下达一次：**“优化大部经典的加载速度，保留阅读位置、书签、心得、简繁切换和现有设计。”**

1. 负责人先确定按章加载的数据契约与兼容要求。
2. 实现A在worktree-A处理构建输出与加载层；实现B在worktree-B处理加载状态与阅读组件。公共类型由负责人先定义或单人负责。
3. 两者返回固定commit/patch和执行证据，负责人按固定base SHA整合。
4. 独立审阅者检查旧段落标识、私人快照、异常网络、简繁与长文定位。
5. 负责人运行 `npm run check:release`，有失败则定向返工，最后向你展示同一提交的结果。只有现有授权覆盖发布时才发布。
6. 按资源归属清理自建测试页、context、服务和可回收worktree；保留用户现有页面与成果。

可以并行的是独立实现与只读探索；接口定义、集成和最终验收通常有顺序。只有测量端到端时间与返工后，才能判断是否提速。

## 我不推荐同时组合的东西

- 不让HMB、T3、AO同时管理同一批Worker的创建、取消和worktree回收。
- 不让多个终端不停修改同一份CC Switch全局默认，以此模拟每Worker渠道隔离。
- 不先安装网关来“统一一切”；协议原生适配足够时，直接接对应CLI更容易定位问题。
- 不把Gemini报告建议的200–300行脚本升级为默认完整平台；一次性测试启动器可以很小，可靠调度与停止恢复需要真实工程成本。
- 不把模型多、消息多或任务卡都变绿当作交付；用本仓库真实门禁与成果身份验收。

## 现在已经确定、还未确定的部分

**已确定：**六套组合的职责拆分和核心连接有官方文档/源码依据；T3内部与外部接口、HMB四种Worker范围、Worktree Kanban串行/并行行为、hc职责边界已核过。详细证据见前两轮报告。

**未确定：**你的具体渠道列表、各渠道的协议/工具调用/限流、所选发行版在这台Windows上的取消与重连结果。它们不妨碍给出上述推荐，但决定最终能启用哪些Worker。没有安装或发真实模型请求，不能说“组合已可直接稳定运行”。

落实顺序：先按组合一做本机版本/渠道无秘密预检，再进行两渠道只读往返；若你明确要保持当前主界面，则改用组合二。通过后才进入双worktree实现、故障/取消回收和真实门禁。验收不达标时退回原单代理流程，保留证据，不强行叠加另一套平台救场。
