# 多模型协作试点交接：核验后的版本

日期：2026-11-21。状态：研究/交接准备完成；没有安装候选、创建试点工作树或执行真实模型请求。依据 [Gemini复核](REVIEW.md) 与项目现行规范。本文件不自动授予额外执行权限。

## 目标

检验一个负责人能否把有边界任务交给不同模型渠道，自动取得可核验成果，并在固定测试条件下减少人工转述与返工。保留用户现有配置、工作区、浏览器和代理7890。

## 采用哪条路线

- 保留现有Codex/Claude/DSH主入口：HMB小试点，优先核固定发布版和原生配置适配。
- 统一桌面与多渠道实例：T3对照试点。主代理在T3内部才使用内部delegate；外部Codex按对应版本的thread API操作，不能混用caller-only能力。
- 重度PR/CI闭环：AO作为后续工作台对照。
- 自写脚本只做单次基准启动/收集探针；不以300行目标承诺持久调度、幂等、跨平台安全收尾。

当前无需先部署网关。只有实际协议不匹配且原生运行时无法承接时再评估；不因出现“兼容API”字样就判断可用。

## 阶段0：无模型请求的准备

1. 确认工作目录、当前分支、固定base SHA、已有worktree/未提交成果。原有工作树组成保留集合，不要求整个机器只剩主库。
2. 记录候选版本、原生CLI路径及版本，按该版 `--help` 核对启动/恢复/输出参数；只读版本入口也可能写初始化日志，异常时停止并记录。
3. 对两条候选渠道仅记录无秘密身份：harness、provider ID、真实model ID、协议、凭据来源类型。不得打印配置全文、环境凭据或复制auth.json。
4. 配置隔离用工具明确支持的实例/配置文件/子进程环境；不在并发父进程不停切全局provider或改共享环境。继承策略、项目hooks/MCP与工作目录分别核对。
5. 复用代理体检，固定7890。如需补回环绕过，保留既有NO_PROXY条目后按需合并，不整串覆盖；宿主自管ALL_PROXY保留。
6. 明确预算、超时、最多并发2与返工上限。未取得实际用量就记unknown，不能因无字段而当0。

完成条件：无未决版本/作用域冲突，配置和资源归属明确。此阶段不运行模型、沙箱初始化、安装器、Job修改或大规模测试。

## 阶段1：单次只读原生往返

在已明确的渠道范围内执行一个极小只读任务，例如读package.json的name并返回。每次任务有唯一run/task/attempt、固定cwd与输入摘要。输出区分：

| 证据 | 记录要求 |
| --- | --- |
| requested | 发给原生CLI的目标provider/model |
| native_readback | 原生运行时报告的实际选择，缺失则unknown |
| provider_reported | 上游响应字段及来源；不可将回显当物理模型证明 |
| completion | 原生最终状态、进程退出、答案格式、产物与检查分别记录 |

Codex `--json`逐行解析为事件流，stdout/stderr分开；使用本机明确支持的schema功能校验答案。正常退出但错误终态、截断事件、未知模型或产物不符均不得算通过。不同CLI恢复参数分别查help，session必须绑定原配置目录、cwd与渠道，不用“最近一次”猜测。

完成条件：各渠道有真实原生往返证据、没有配置串线，临时执行资源确认停止。该阶段成功仍不证明并发与恢复通过。

## 阶段2：并行只读协作

由同一负责人向两个明确Worker派发互相独立的问题，返回实际代码引用和验收建议。上下文只含目标、相关路径和不变量，不传整个对话。

负责人发一次有界补充说明，确认目标Worker/Session身份和返回结果。记录原生执行事件与任务时间，不能只由state.json区间重叠推断服务器真正同时推理。

Reviewer使用独立会话和已验证只读工具/权限组合。禁写工具、shell与无关MCP的方式须按选定runtime验证；`--allowedTools`、worktree和git status为空都不能单独证明严格只读。

## 阶段3：隔离实现与统一集成

1. 选低风险、互不重叠的两项真实修改；冻结共同接口、基线提交、验收条件和文件所有权。沿用用户已有授权，不因文档模板再造重复审批。
2. 仅为本次run准备独立worktree，采用项目要求的分支前缀。若确有短路径需求，使用带唯一run标识的目录；路径不应成为跨run共享的删除目标。
3. 未提交/未跟踪输入若需要带入，由负责人显式选择并记录；默认不复制凭据与忽略目录。各依赖和产物独立，确认Windows硬链/权限行为，不拿worktree当系统沙箱。
4. 结果固定到commit/tree或完整二进制安全patch；核对提交后差异和未提交/未跟踪文件，所有输出必须在任务范围内。
5. 只在本次集成worktree整合明确成果，处理冲突后执行 `npm run check:release`。此命令包含文档、lint、类型、内容/Pages构建、静态/解析与浏览器回归；`test:e2e`不得验证旧dist。
6. 测试使用现有E2E_PORT、strictPort与自有headless context；端口占用时改本次测试端口或失败，不停用户服务。最后记录同一集成提交的门禁和独立审阅。

源码完成、审阅通过、测试通过和发布是分开的状态；本试点结果不自动触发主分支合并、push或Pages部署。

## 阶段4：恢复与停止的必要语义

优先复用已核实现的任务宿主。若实现简小启动器，不能仅凭PID+taskkill宣称可靠全树控制。

- 记录run/task/attempt、创建时间、原生session、进程handle或可核验归属、固定输入/输出摘要；Windows使用适用的受管Job并验证加入成功，不能盲杀名称匹配的进程。
- 任务状态至少区分queued、running、cancel_requested、stopping、delivered、accepted、failed和shutdown_unknown。发出取消不等于已停止；端口关闭也不证明所有子进程消失。
- 启动意图、启动结果和完成回执间的崩溃窗口需要恢复核对。结果不明时先检查已有执行，禁止把同一逻辑工作作为新任务重派。
- 429要区分原生runtime内部重试与编排层重试。模拟429→200只验退避逻辑，不能当原生CLI链路验证；遵从实际可见的拒绝与上限，不按所有错误统一重试。
- shutdown_unknown时保留工作树、日志及执行槽位，不自动重派或删除。

故障测试覆盖：根进程先退出、取消时仍派生、回执丢失、调度器重启、受管资源与用户原有进程并存。测试应在专用演练副本中进行，不能用真实用户工作作故障注入材料。

## 清理与回退

以本次创建清单为唯一清理范围。规范化绝对路径，核对资源身份和链接/reparse point边界；固定可恢复产物后只移除本次干净worktree。移除失败就保留并报告，禁止随后递归删除共享父目录。

配置目录可能保存登录资料，默认保留；不因试点结束自动清空。分支、worktree、浏览器标签和服务均只处理有明确本次归属的对象；不能要求“所有进程与开始时完全一致”或“全仓库只剩一个worktree”。

验收是：本次已确认可回收的资源释放，原有资源与用户成果保留；未知项列出。原始报告P186的共享目录强删命令不得使用。
