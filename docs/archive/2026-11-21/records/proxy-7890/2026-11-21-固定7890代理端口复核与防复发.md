# 固定7890代理端口的复核与防复发流程

## 背景

用户明确要求所有普通代理客户端继续使用127.0.0.1:7890，不接受通过改到7970来绕过故障。此前DSH把Windows异常的TCP动态范围恢复为49152–65535，并重启WinNAT释放旧排除段。本轮复核实际结果并修正体检/修复脚本。

## 内容

### 已确认的事实

- 2026-11-21复核时7890由verge-mihomo（Clash内核）监听，PID25168；不是其他进程抢占。
- IPv4/IPv6的TCP、UDP动态端口范围均为49152起、16384个；四类排除端口均不包含7890。
- verge.yaml的verge_mixed_port、config.yaml的mixed-port、生成的clash-verge.yaml的mixed-port均为7890；系统代理启用且指向127.0.0.1:7890；用户HTTP_PROXY/HTTPS_PROXY为http://127.0.0.1:7890。
- 显式经7890请求Microsoft和GitHub，TLS CONNECT及HTTP均200；刷新当前测试终端环境后，不指定--proxy的curl也通过环境变量走7890成功。
- Clash原日志显示06:39绑定7890出现os error10013后，本会话回退7902；10:42又回退7970。GUI的“externally occupied”文案不等于存在抢占进程。
- 先前修复日志确实记录IPv4 TCP动态范围start1024/count13977，修复后49152/count16384。用户提供的7870–7969旧排除段本轮已不存在，不为复现重新创建。
- 现有证据支持“异常低位动态范围与旧端口排除造成绑定失败”的历史解释，但不能确定哪个程序最早修改动态范围，不能断言一定由Docker、WSL或某智能体修改。有限工具目录与相关任务检查未找到明确修改来源。
- Windows名称为Proxy的任务运行rundll32/acproxy.dll，不因名字包含Proxy就认作改端口的程序。

### 重要纠正

10013表示访问/绑定被拒绝，独占绑定也可能产生该错误；10048通常表示地址已使用。应同时看监听PID、排除范围和具体日志，不能只凭错误码推断。参考微软Winsock错误码文档。

用户级环境变量写入注册表不会自动更新已经运行的终端、Codex、DSH或其父进程。只重开某个子终端也可能仍继承旧桌面宿主环境。本轮执行环境最初HTTP_PROXY/HTTPS_PROXY未设置；必须与User层分开报告。工具支持情况不同：设置环境变量不代表所有SDK会自动使用代理。

此前研究子代理还有明确的429限流错误，这与代理端口错误是不同问题，不能用一个原因解释全部无响应。

### 已完成的工具修正

工具目录为当前用户的 .agents/tools/：

- check-proxy-ports.ps1：固定检查7890的地址和进程归属，验证持久/生成Clash设置、系统代理启用状态、HTTP/HTTPS完整映射、Process/User/Machine环境、IPv4/IPv6 TCP/UDP动态及排除范围。默认做两次显式代理HTTPS请求；失败exit1，成功exit0。-SkipNetwork只验配置，-AsJson输出已脱敏结构。
- proxy-port-common.ps1：共用解析与判定。系统分协议映射和环境变量单URI分别处理；未知读取结果不能当健康。不会输出密码、订阅、代理节点、NO_PROXY具体内容。
- proxy-port-fix.ps1：默认诊断；健康时即使带Apply也直接退出。只有明确动态范围漂移且管理员执行-Apply才恢复默认；7890仍被非人工排除时，另需-RestartWinNat且Clash已退出、WinNAT原为运行态。停止/恢复都有有界等待和失败结果。该重启会影响NAT相关工作，不能当日常通用修复。
- use-fixed-proxy.ps1：确认User层与7890监听后，仅在当前PowerShell进程设置HTTP_PROXY/HTTPS_PROXY，供之后启动的命令继承。保留ALL_PROXY/NO_PROXY，不能远程更新已运行桌面程序。
- tests/proxy-port-consistency.tests.ps1：22项纯数据回归，包括全端口一起漂移、错误PID、空配置、IPv6排除、旧环境、错误URL、缺HTTPS映射、网络失败等。

原脚本已备份至 .agents/tools/backups/proxy-7890-review-20261121/。本轮没有停止Clash/WinNAT/HNS，没有新增系统端口排除，没有关闭Hyper-V/WSL，也未改全局执行策略。

### 日常一条体检

```powershell
powershell -NoProfile -File "$env:USERPROFILE\.agents\tools\check-proxy-ports.ps1"
```

只检查配置：加-SkipNetwork。输出PASS且两站网络成功说明当次代理链路可用；如果进程环境缺失会单独警告，不能忽略。

若当前终端环境旧，在准备启动git/npm/curl等工具的同一个PowerShell里运行：

```powershell
. "$env:USERPROFILE\.agents\tools\use-fixed-proxy.ps1"
```

若是已运行桌面智能体宿主环境旧，在保存任务后正常重启该应用；不要强杀进行中的工作。不要通过另开powershell -File运行环境刷新脚本后，误以为父终端已经变化。

### 只有系统范围再次异常时

先体检保存证据，检查是否有真正占用7890的进程。动态范围确实异常才在管理员终端执行：

```powershell
powershell -NoProfile -File "$env:USERPROFILE\.agents\tools\proxy-port-fix.ps1" -Apply
```

若仍存在覆盖7890的动态排除段，先保存Docker/WSL/虚拟机相关工作并退出Clash；检查后才使用同一命令追加-RestartWinNat。脚本不会删除人工管理的排除段，不自动结束其他占用进程，不自动改成备用端口。Clash重开后再运行完整体检。

### 防复发原则与验证范围

固定7890贯穿配置与环境；Windows动态范围保持默认高位，避免把7890放进动态分配范围。系统/虚拟化/代理升级、重启后或首次联网失败时先体检，不无限重试，不把环境跟着临时端口漂移。

不以计划任务周期性重启WinNAT，不给7890添加“排除端口”来保护它（可能反而阻止普通应用绑定）。故障不再发生不能被绝对保证：尚未做系统重启后的验证，也未定位最初修改动态范围的程序。

本轮22项回归通过；模拟Process HTTP_PROXY=7970时完整检查exit1，刷新进程后检查exit0、无warning，两站HTTP200；带Apply/RestartWinNat运行健康路径确认no-op，内核PID保持25168。
